AI-Powered Sorting Machine

Engineer a custom automated sorting machine that recognizes parts with AI vision and physically routes them into the correct collection bins.

Engineering Design Challenge

Your Mission

Working in a team of 2–3 students, design, fabricate, program, and test a computer-connected, AI-powered sorting machine that uses a trained model to identify parts and automatically move them to the correct destinations. Choose either LEGO components or nuts and bolts. Each team defines three visually distinguishable sorting classes and builds three product bins plus a fourth reject bin for unknown or uncertain items.

100 points60 engineering + 40 performanceManual loading allowedFully custom construction

Option A: LEGO Components

Choose three different part types or shapes, such as 2×2 bricks, 2×4 bricks, and plates. The classifier must recognize part identity or shape; simply sorting by color is insufficient.

Option B: Nuts & Bolts

Choose three distinct hardware categories—for example, nuts, short bolts, and longer bolts. Use clean, instructor-approved, blunt hardware. Your camera and feeder must handle glare and variable object positions.

Preparation: Complete ADM 2.1.8–2.1.10 in Programming Studio before this final project. Those guided lessons prepare the sensor, vision and actuator skills; the final project still requires your own trained classifier, design and supervised physical validation.

Required equipment and programming

  • Camera: external USB webcam (available from the instructor).
  • Computer: classroom Windows computer running Python with OpenCV through a browser-based interface. Use LockwoodSTEM Programming Studio in desktop Chrome or Edge over HTTPS for USB Arduino access. Python and OpenCV run in the browser; no local Python installation or notebook server is required.
  • Vision and programming: train your image classifier in Model Builder, then write and explain your control logic in Programming Studio. Reuse and adapt the ideas from lessons 2.1.8–2.1.10 and Studio’s Custom classifier starter. You must design your own class-to-bin mapping, decision rules, timing, and test procedure. Studio has no AI coding assistant.
  • Required hardware controller: every team must use the instructor-provided Arduino to operate its sorting mechanism. Use a board prepared with the standard Studio firmware. The built-in bridge supports one servo (0–180°), the built-in LED, and an A0 sensor. Design a single-servo chute or gate that can reach all four bins. Additional motors, servos, or arbitrary pin control are outside the current Studio bridge and require a separately approved extension.
  • Fabrication: student-selected, teacher-approved methods (3D printing, laser cutting, hand tools, or other techniques). No fixed additional materials budget, but all purchases require approval.
How it works: USB webcam → saved Model Builder classifier → predictions supplied to Python in Studio → awaited Arduino commands → simulated or physical servo → three class bins or reject bin.
First approval gate: show a live camera frame, a saved classifier prediction in Studio, and Python control of the simulated servo. Record this as simulation evidence. Before powered fabrication/integration, separately verify the actual classroom computer, prepared Arduino, wiring, unloaded servo travel, and Stop behavior. Simulator success does not provide physical hardware approval.
Your project workspace

Build the sorter in Programming Studio

Use the lesson panel, editor/console, and device panels together. Run/Stop controls stay at the top; on smaller screens use the Lesson, Code & console, Simulator, and Camera shortcuts.

1. Plan four destinations and a repeatable camera view

Choose three product classes that differ in shape or identity, plus a reject destination. Fix the camera and lighting and present one part at a time. The custom classifier labels the whole frame; it does not locate several parts or produce custom bounding boxes. Plan a consistent presentation area and four safe servo positions. Sketch how a physical part moves from that view into each bin.

2. Train and check your model in Model Builder

  1. Open Model Builder. Add your three class names, choose Image category, and capture or upload labeled images. Collect 75 distinct images per class (225 total), varying pose and lighting without changing the meaning of each label.
  2. Select Train classifier. Model Builder uses MobileNet features and a nearest-centroid classifier, with a deterministic one-in-five held-out split per class. With exactly 75 images per class, it uses 60 for training and 15 for testing: 180 training and 45 test images overall. Record the displayed counts and accuracy.
  3. Use Start live prediction with fresh physical examples. Test incorrect poses, an empty view, and unfamiliar objects as well as known parts. Do not treat repeated near-identical frames as independent evidence. Once you tune using the displayed test results, those results are development feedback; use fresh examples for your final evaluation.
  4. Select Export model to save the classifier JSON. Use Export annotated ZIP to back up the collected images; boxes are not required for this whole-image classifier. Stop the Model Builder camera before returning to Studio.

The saved classifier stays in this browser profile on this site. On another computer or profile, import your exported classifier in Model Builder first. Project submission files and Python exports do not include the classifier or image dataset.

3. Create your named Studio program

  1. Open Programming Studio, select New project, and name it team-name-sorter.py. Your prior projects remain available in Saved projects.
  2. In Launch a program, choose Custom classifier and confirm replacement only in this new project. This starter displays predictions; it is not a finished sorting program. Choose Live vision in Run mode.
  3. Start the camera. In Vision lab, expand AI models & custom classifier and select Load saved classifier. Wait for Model ready. Use your trained classifier, not the generic object detector.
  4. Select Run live. The starter draws the predicted label and score in the processed preview. Test known parts and empty/unknown scenes before adding actuator commands. Stop before changing code, restart Python, restart the camera, and reload the saved classifier if needed.

4. Turn predictions into a tested decision

During each frame, get_custom_prediction() returns a list sorted by score, with label and score for each class. An empty list means no custom predictions are available; handle it explicitly. Python reads predictions produced by the browser model rather than loading a separate Python model file.

# Inside process_frame(frame): inspect before controlling a gate.
predictions = get_custom_prediction()
if predictions:
    best = predictions[0]
    label = best["label"]
    score = best["score"]

Use async def process_frame(frame) when sending commands such as await arduino.servo(angle) or await arduino.led(True); return the annotated frame for the processed preview. await arduino.sensor() reads A0 if your design uses it. Do not add desktop serial libraries, port names, or a second Arduino protocol.

Your control design must explain: the mapping from each exact class label to a calibrated servo angle; the reject rule; persistence across consecutive frames; when a new part is present; when a decision is latched; how the part clears; and when the next cycle is allowed. Reuse the candidate/streak idea from 2.1.10, but a stable label alone must not count the same stationary part as several completed sorting trials. Keep frame callbacks brief so the preview can keep updating.

Scores are not certainty: this classifier always compares known classes and may give an unfamiliar object a high score. A score threshold alone is not a guaranteed unknown detector. Test unknown and empty scenes, compare the top two scores, consider an explicitly trained background/reject class, and use an approved safe stop/handling rule when evidence is insufficient. If you add a fourth class, collect another 75 images and report the updated split separately.

5. Validate decisions with the simulator

Choose Simulator in Hardware lab, then Arm hardware before Run live. Verify all four commanded positions using real camera scenes; use the A0 slider if your logic needs a sensor. Record expected label, observed label/score, chosen destination, commanded angle, and result. Test missing predictions, brief appearances, repeat frames, Stop, and tab switching. Record these as simulated routing, not physical sorting accuracy.

6. Transfer the same program to USB Arduino

After the physical setup is approved, Stop first. Choose USB Arduino, Connect board, select the prepared board, and wait for firmware confirmation. Start the camera, load the saved classifier, Arm hardware, and Run live. Begin with an unloaded servo, then test the guarded mechanism. The Python API stays the same. Studio does not upload firmware or control unsupported motors automatically.

Stop ends Python, disarms outputs, and closes the camera. A detached servo is not a mechanical brake. Switching away from Studio also stops the program and devices. Keep the page visible during a physical trial and stop immediately for a jam.

7. Save evidence and submit

Use Export submission for the named .studio.json project with code, run settings, input, and applicable console evidence. Also export .py, the classifier JSON from Model Builder, dataset ZIP, test logs, and design files. A standalone capstone project has no automatic lesson reflection checklist: include your trial log and reflection as separate documents. Downloading a file does not submit it; upload the complete package through your classroom assignment.

Minimum Requirements

Mechanical, AI, and Testing Specifications

Custom machine

  • Three student-selected part classes, three collection bins, and one unknown/reject bin.
  • Custom frame, object presentation area, fixed webcam mount, powered sorting mechanism, and secure collection bins.
  • Manual loading of one object at a time is allowed. Classification and routing after insertion must be automatic.
  • Use a single-servo gate or rotating chute with four calibrated destinations supported by the standard Studio bridge.
  • Automatic hopper feeding, additional categories, or higher sorting speed are optional extensions without bonus points.

AI training

  • Collect 75 labeled images for each of three classes: 225 distinct images total for Model Builder.
  • Model Builder holds out one in five images per class: 60 training + 15 test images per class, or 180 training and 45 held-out test images. Keep fresh live examples separate for later validation.
  • Submit the exported Model Builder classifier JSON, dataset ZIP, documented training procedure, sample predictions, and overall validation accuracy.
  • Use actual model predictions to drive the sorter. Studio supplies camera frames and custom predictions to Python; OpenCV can annotate and analyze those frames, but color thresholds, fixed timers, or hand-picked classes alone do not qualify.
  • Uncertain or unfamiliar parts must route to reject or trigger an approved safe handling procedure.
Final demonstration: 30 randomized trials (10 from each known class) plus 5 separate unknown/reject trials—35 trials altogether. The target is 80% known-part accuracy (at least 24/30 correct), with advanced recognition for 28–30 correct. Track throughput, resets, jams, and one evidence-based improvement. The instructor chooses the random presentation order.

Safety

Use approved low-voltage power supplies and secure wiring. Verify the Arduino-to-servo electrical design before activation: a servo may need its own properly rated power source and a shared ground. Guard pinch points, keep hands clear when powered, wear safety glasses while fabricating, and stop if parts jam. Do not use unapproved mains wiring, sharp or hazardous objects, or unsupervised powered testing.

What counts as success?

The machine recognizes a previously unseen physical object using the trained classifier, automatically commands the Arduino, and routes the object to the correct bin. A screen-only demonstration, manually controlled servo, or fixed sorting sequence does not complete the physical final assessment. If hardware is unavailable, finish and submit the model, code, simulation trials, and design evidence as progress; mark physical build and performance evidence as pending.

Extended engineering project · Approximately 40 × 45-minute classes

Project Timeline & Graded Milestones

Plan for approximately 40 class periods (30 instructional hours) for independent AI development, custom fabrication, Arduino integration and iterative testing. Use the live Daily Agenda and classroom assignment for official deadlines. Teams can work on multiple parts of the project in parallel, but must receive approval before moving past safety-critical checkpoints.

Phase 1 · 5 classes

Research, environment setup & system proposal. Choose LEGO or hardware and three distinct sorting categories; open Model Builder and Studio. Confirm webcam capture, saved model predictions and simulated servo commands; schedule the separate physical USB check, draw two viable concepts and assign team responsibilities.

Checkpoint 1 · 10 points: Feasibility and design proposal.

Phase 2 · 8 classes

Training data & AI development. Gather 225 labeled images, train in Model Builder, record the 180/45 split and displayed accuracy, then test fresh live examples in Studio. Refine lighting, camera placement and decision/reject rules. Sketch preliminary machine layouts in parallel.

Checkpoint 2 · 15 points: Trained classification model and evidence.

Phase 3 · 7 classes

Mechanical design & manufacturing preparation. Create assembly CAD or dimensioned drawings of the feeder, camera mount, sorter and four bins. Select materials, prepare fabrication files, evaluate required servo motion and create a safe wiring/power plan. Begin approved fabrication when ready.

Intermediate progress review: Manufacturing-ready design and approved bill of materials; incorporated into Checkpoint 3.

Phase 4 · 10 classes

Fabrication, assembly & mechanism iteration. Build, fit and revise parts; secure the webcam and sorting components; connect the prepared Arduino through Studio USB mode and drive the unloaded servo under controlled tests. Account for printer queues, failed fits and rebuilding. Recheck wiring and travel after any extended pause.

Checkpoint 3 · 15 points: Completed safe custom assembly and electronics demonstration.

Phase 5 · 7 classes

AI-to-Arduino integration & debugging. Link saved classifier predictions to awaited Studio servo/LED commands, first in simulation and then on the approved board. Route objects into all three class bins and reject; record misclassifications, delays and jams. Run mixed trial batches, revise the code or mechanism, and retest.

Checkpoint 4 · 15 points: Live autonomous sorting through every destination.

Phase 6 · 3 classes

Test readiness, final demonstration & analysis. Complete preflight checks, document a measured improvement and organize technical files. Demonstrate 30 randomized known parts (10 from each class) plus five separate unknown/reject items, then review accuracy, throughput and reliability.

Checkpoint 5 · 5 points: Final test readiness.

Final performance · 40 points: Supervised assessment.

Scheduling: the six phases total approximately 40 classes. Hardware-dependent approvals and final physical testing remain pending until equipment is available and approved. Follow the Daily Agenda and classroom assignment for dates; this page does not reschedule those systems.
Evidence submitted throughout the project

What to Submit

  1. Checkpoint 1 — Proposal: two concepts, chosen class definitions, system architecture, team roles, hardware/material plan, safety plan, and Studio webcam and simulated-command evidence, with the physical USB check recorded separately.
  2. Checkpoint 2 — AI model: 225-image dataset ZIP, exported classifier JSON, 180/45 split and held-out accuracy, fresh live prediction results, and an explanation of errors.
  3. Checkpoint 3 — Build: CAD or fully dimensioned technical drawings, fabrication files, parts list, photographs, Arduino wiring, and physical mechanism approval.
  4. Checkpoint 4 — Integration: named Studio submission (.studio.json), commented Python export (.py), exported classifier JSON, decision/state diagram, simulation logs, and the approved physical demonstration of all three routes plus reject. Identify the standard firmware used; do not submit a newly invented Arduino protocol.
  5. Checkpoint 5 — Readiness: safety/preflight checklist, debugging records, evidence of one improvement, and organized submission files.
  6. Final assessment: 30 known-object and five unknown-object trial results, calculated known-object accuracy and throughput, failure/reset record, final demo, and short reflection.

Each checkpoint is graded separately. Keep CAD, dataset ZIP, classifier JSON, Studio submission, Python export, test logs, reflection, and build documentation in a clearly organized team folder. The Studio project export does not package the model, dataset, CAD, or physical evidence. Document your code changes and tests. Everyone must be able to explain their contribution and code. If a checkpoint is incomplete, revise and request reapproval before moving to the next safety-critical stage.
